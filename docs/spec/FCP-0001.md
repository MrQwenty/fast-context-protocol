# FCP-0001: Fast Context Protocol 0.1

- Status: Draft
- Version: 0.1.0
- Date: 2026-08-01
- Editors: Matteo Pelosi

## Abstract

The Fast Context Protocol (FCP) is an open, model-agnostic protocol for discovering, negotiating, compiling, transporting, updating, and verifying context for AI systems under explicit latency, token, freshness, privacy, and quality constraints.

FCP defines a control plane for context discovery, policy, negotiation, and planning, plus a data plane for delivery, caching, deltas, and progressive streaming. FCP does not define model inference or general-purpose tool execution.

## 1. Scope

FCP 0.1 standardizes:

- provider discovery and capability negotiation;
- structured context requests;
- budget-aware context planning;
- content-addressed context chunks;
- inline and cached-reference delivery;
- provenance and freshness metadata;
- consumer receipts.

The following remain experimental:

- binary framing;
- semantic delta encoding;
- long-lived subscriptions;
- cryptographic attestations;
- distributed context graph federation;
- model-specific compilation profiles.

## 2. Terminology

**Consumer**: an application, agent runtime, model gateway, or compiler requesting context.

**Provider**: a service exposing context descriptors and content.

**Context node**: a typed, versioned unit of context with metadata and a stable content digest.

**Context graph**: nodes and typed relationships relevant to an operation.

**Context plan**: the provider's ordered selection and delivery strategy for a request.

**Known context**: content digests already available to the consumer.

**Receipt**: the consumer's record of what was received, reused, rejected, or omitted.

## 3. Protocol model

FCP separates two logical planes.

### 3.1 Control plane

The control plane handles discovery, version negotiation, authorization context, budgets, policies, context planning, provenance, and invalidation.

### 3.2 Data plane

The data plane transports content chunks, references, patches, and progressive streams. FCP 0.1 uses JSON over HTTP. Future versions may negotiate CBOR, MessagePack, Protobuf, or binary frames.

## 4. Versioning

Consumers send the protocol version in `FCP-Version`. Providers MUST return the selected version using the same header.

FCP 0.1 uses:

```text
FCP-Version: 0.1
Content-Type: application/fcp+json
```

A provider that cannot support the requested major version MUST return HTTP `426 Upgrade Required` and advertise supported versions.

## 5. Core endpoints

### 5.1 Discovery

```http
GET /.well-known/fcp
```

Returns provider identity, supported protocol versions, endpoints, limits, delivery modes, and optional features.

### 5.2 Resolve

```http
POST /fcp/v0.1/context/resolve
```

Accepts a `ContextRequest` and returns a `ContextPlan`.

### 5.3 Fetch

```http
GET /fcp/v0.1/context/{digest}
```

Returns one context node when policy permits.

### 5.4 Receipt

```http
POST /fcp/v0.1/receipts
```

Records delivery and reuse outcomes. Providers MAY ignore receipts.

## 6. Context request

```json
{
  "requestId": "req_01JX",
  "intent": {
    "type": "code.review",
    "target": "pull-request:482"
  },
  "consumer": {
    "id": "example-agent",
    "modelFamily": "generic-transformer",
    "contextWindow": 128000,
    "modalities": ["text"]
  },
  "budget": {
    "maxTokens": 12000,
    "maxLatencyMs": 80,
    "maxBytes": 524288
  },
  "requirements": {
    "freshnessMs": 5000,
    "minimumConfidence": 0.8,
    "includeProvenance": true
  },
  "knownContext": ["sha256:..."]
}
```

### 6.1 Budget semantics

A provider MUST NOT intentionally exceed `maxTokens` or `maxBytes`. If no complete plan fits, it SHOULD return the highest-utility partial plan and set `complete` to `false`.

`maxLatencyMs` is a planning objective, not a hard real-time guarantee. Providers SHOULD include their estimated planning and delivery latency.

### 6.2 Selection objective

A conforming resolver SHOULD maximize expected task utility while respecting policy and hard budgets. A baseline scoring function is:

```text
score(node) = relevance * confidence * freshnessFactor * priority
              / max(1, tokenCost)
```

Implementations MAY use more advanced ranking, provided results remain explainable through selection reasons.

## 7. Context plan

A `ContextPlan` contains:

- a unique plan identifier;
- root digest for the selected graph;
- estimated tokens, bytes, and latency;
- completeness indicator;
- ordered chunks;
- omissions with machine-readable reasons.

Delivery modes in FCP 0.1:

- `inline`: content is included in the plan;
- `reference`: the consumer is expected to already possess the digest;
- `fetch`: content can be retrieved from the fetch endpoint.

Chunks MUST be ordered by decreasing delivery priority. Consumers MAY begin processing before all fetch-mode chunks arrive.

## 8. Content identity

Immutable content MUST be addressed as:

```text
sha256:<lowercase-hex-digest>
```

The digest is computed over the canonical content bytes, not the surrounding metadata. JSON content SHOULD use RFC 8785 JSON Canonicalization before hashing.

## 9. Metadata

Every node MUST declare:

- `id`;
- `type`;
- `contentType`;
- `tokenEstimate`;
- `byteLength`;
- `priority`;
- `confidence`;
- `createdAt`;
- `provenance`.

Nodes SHOULD declare:

- `version`;
- `freshUntil`;
- `sensitivity`;
- `relationships`;
- `transformations`;
- `signature`.

A generated summary MUST identify both the source material and the transformation that produced it.

## 10. Policy and privacy

Providers MUST enforce authorization before ranking or delivering restricted nodes. Unauthorized content MUST NOT be disclosed through titles, token estimates, omissions, timing differences intentionally introduced by implementation, or other metadata.

Sensitivity values in 0.1 are:

- `public`;
- `internal`;
- `confidential`;
- `restricted`.

Consumers SHOULD declare accepted sensitivity levels and data-handling capabilities. Providers retain final authority.

## 11. Errors

Errors use `application/problem+json` and SHOULD include:

```json
{
  "type": "https://fcp.dev/problems/budget-unsatisfied",
  "title": "Context budget cannot be satisfied",
  "status": 422,
  "detail": "No authorized node fits the declared token budget.",
  "requestId": "req_01JX"
}
```

Recommended status codes:

- `400`: malformed request;
- `401`: missing authentication;
- `403`: policy rejection;
- `404`: unknown digest;
- `409`: stale plan or invalid base digest;
- `413`: request or result too large;
- `422`: valid request with unsatisfied constraints;
- `426`: unsupported protocol version;
- `429`: provider capacity exceeded.

## 12. Receipts

Receipts improve observability and future ranking. A receipt MAY report:

- delivered digests;
- reused digests;
- rejected digests;
- actual tokens consumed;
- time to first context;
- total delivery latency;
- optional task outcome signal.

Outcome signals MUST be opt-in and SHOULD avoid raw user content.

## 13. Conformance levels

**FCP Provider Core** supports discovery, resolve, inline delivery, content digests, budgets, and provenance.

**FCP Provider Cache-Aware** additionally supports known-context references and fetch.

**FCP Provider Streaming** additionally supports progressive streams and cancellation.

**FCP Provider Verifiable** additionally signs manifests or nodes and publishes verification material.

## 14. Security considerations

Implementers must consider prompt injection contained in sources, confused-deputy authorization, cross-tenant cache leakage, digest confusion, malicious token estimates, decompression bombs, replayed plans, traffic analysis, and provenance forgery.

Context content is untrusted data. Consumers MUST NOT interpret instructions embedded in context as protocol directives.

## 15. Relationship to adjacent protocols

FCP focuses on context selection and delivery. Tool execution, inter-agent delegation, model inference APIs, identity federation, and general workflow orchestration are outside its core scope. Adapters may convert external resource and tool results into FCP context nodes.

## 16. Open questions for 0.2

- canonical semantic patch format;
- graph query language;
- portable authorization claims;
- cross-provider plan composition;
- deterministic token estimation profiles;
- privacy-preserving relevance scoring;
- transport-level backpressure and cancellation.
