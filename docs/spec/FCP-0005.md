# FCP-0005: Local Privacy Gateway and Anonymization Receipts

- **Status:** Draft
- **Protocol version:** FCP 0.1+
- **Category:** Privacy and context safety

## Abstract

FCP-0005 defines a local, fail-closed privacy pipeline that transforms documents before any content is sent to an external model or context provider. It introduces privacy policies, irreversible anonymization, reversible pseudonymization with an encrypted local vault, post-transform leak scanning, privacy receipts, and resolver requirements that can exclude context without acceptable privacy evidence.

The privacy gateway is a consumer-side trust boundary. The original document MUST remain local. Only extracted and sanitized context, plus non-sensitive verification metadata, may cross the boundary.

## 1. Goals

An implementation conforming to this specification is designed to:

1. prevent original documents and metadata from reaching an external LLM;
2. detect direct identifiers, credentials, financial identifiers, and configured domain identifiers;
3. preserve enough semantic structure for useful model inference;
4. prove which policy and processor produced a sanitized node;
5. block unsupported or insufficiently inspected documents in fail-closed mode;
6. keep re-identification mappings local and encrypted when pseudonymization is reversible;
7. make residual privacy risk explicit instead of claiming perfect anonymity.

## 2. Terminology

### 2.1 Redaction

Replacement of a detected span with a non-identifying marker such as `[REDACTED:EMAIL]`.

### 2.2 Pseudonymization

Replacement of identifiers with stable surrogates within a declared scope. Pseudonymized data remains linkable through additional information and MUST still be treated as sensitive. Reversible mode stores the replacement-to-original mapping only in an authenticated encrypted vault under local control.

### 2.3 Anonymization

Replacement with per-document unlinkable surrogates and no retained re-identification mapping. An implementation MUST NOT represent automated transformation alone as a legal guarantee of anonymity. Contextual and quasi-identifier re-identification risk requires separate assessment.

### 2.4 Residual risk

A normalized score from 0 to 1 produced by a post-transform scan. The score is an implementation signal, not a legal determination.

## 3. Trust boundary

```text
Original file
    ↓ local only
Format extraction / OCR
    ↓
Metadata and embedded-object discard
    ↓
Detector ensemble
    ↓
Redact / pseudonymize / anonymize
    ↓
Independent post-transform leak scan
    ↓
Policy gate
    ├── pass → sanitized ContextNode + PrivacyReceipt
    └── fail → block; do not transmit original or partial output
```

The original binary MUST NOT be sent to an external extraction API. Local command-line extractors or local models are permitted. A remote processor MUST NOT advertise `localOnly: true`.

## 4. Supported document handling

A privacy gateway SHOULD support:

- UTF-8 text, Markdown, CSV, JSON, XML, YAML, and HTML;
- DOCX, PPTX, and XLSX through local OpenXML inspection;
- text PDFs through a local PDF extractor;
- scanned PDFs and images through local OCR;
- custom extractors registered by media type.

When a file cannot be fully inspected, a fail-closed implementation MUST reject it and MUST NOT forward the original file as a fallback.

Sanitized context is text or structured data derived from the document. The original binary, document properties, revision history, embedded files, macros, EXIF data, and other metadata are not forwarded unless independently sanitized and explicitly requested.

## 5. Privacy policy

```json
{
  "mode": "anonymize",
  "localOnly": true,
  "failClosed": true,
  "reversible": false,
  "entityTypes": ["PERSON", "EMAIL", "PHONE", "ADDRESS", "IBAN"],
  "customTerms": ["Project Aurora"],
  "allowList": ["Example Corporation"],
  "minimumConfidence": 0.85,
  "maxResidualRisk": 0.0
}
```

- `mode` MUST be `redact`, `pseudonymize`, or `anonymize`.
- `localOnly` MUST be true for FCP-0005 local privacy processing.
- `failClosed` SHOULD default to true.
- `reversible` MAY be true only in `pseudonymize` mode.
- `minimumConfidence` controls which detector findings are transformed.
- `maxResidualRisk` controls the post-transform policy gate.
- `customTerms` adds organization-specific identifiers.
- `allowList` prevents intentional public values from being transformed.

## 6. Detection

A conforming implementation MUST support pluggable detectors. A production deployment SHOULD combine:

- structured validation for email, phone, IP address, IBAN, payment card, tax identifiers, account identifiers, API keys, and tokens;
- contextual extraction for labeled names, addresses, dates of birth, organizations, and record identifiers;
- multilingual named-entity recognition running locally;
- organization dictionaries and allow lists;
- domain detectors for health, legal, financial, HR, and government records;
- multimodal OCR and image-region inspection where applicable.

Pattern matching alone is not sufficient for a production anonymity claim. Overlapping detections MUST be resolved deterministically.

## 7. Transformations

### 7.1 Redaction

```text
mario@example.com → [REDACTED:EMAIL]
```

### 7.2 Scoped pseudonymization

```text
mario@example.com → <EMAIL:6F0A7C21D4B2>
```

The same original value and scope SHOULD produce the same surrogate. Different scopes SHOULD produce different surrogates. The pseudonymization secret MUST remain local.

### 7.3 Per-document anonymization

```text
Mario Rossi → <PERSON_001_A18F2C>
```

Repeated occurrences inside the same document SHOULD remain consistent. The same original value in another document MUST NOT be linkable through the surrogate.

## 8. Reversible local vault

When `reversible: true`, the gateway MAY produce a `SealedPrivacyVault` using AES-256-GCM. The vault MUST remain outside the context plan, never appear in a ContextNode or PrivacyReceipt, be stored separately from sanitized documents, require a locally controlled key, and fail authentication when modified or opened with the wrong key.

## 9. Privacy receipt

A successful transformation produces a receipt containing no original values:

```json
{
  "receiptId": "privacy:44fd...",
  "documentId": "contract-2026-08",
  "mode": "anonymize",
  "policyDigest": "sha256:...",
  "inputDigest": "sha256:...",
  "outputDigest": "sha256:...",
  "processor": "fcp-local-privacy-gateway",
  "processorVersion": "0.1.0",
  "localOnly": true,
  "failClosed": true,
  "reversible": false,
  "detected": 12,
  "transformed": 12,
  "unresolved": 0,
  "entityCounts": {"PERSON": 2, "EMAIL": 3, "PHONE": 1},
  "residualRisk": 0,
  "passed": true,
  "createdAt": "2026-08-03T09:00:00Z"
}
```

The receipt MAY be signed. A signature covers the canonical receipt, sanitized output digest, and policy digest.

## 10. Context node metadata

A sanitized node carries only receipt-derived metadata: mode, receipt identifier, source and sanitized digests, residual risk, entity counts, and processor identity. The reversible mapping never travels with the node.

## 11. Resolver enforcement

A ContextRequest MAY require sanitized context and set `maxResidualRisk`. A provider SHOULD omit a node when privacy metadata is absent, its status is not sanitized, its residual risk exceeds the declared maximum, or a required receipt signature cannot be verified.

Recommended omission reasons are `privacy-receipt-required`, `privacy-risk-above-maximum`, `privacy-signature-invalid`, and `privacy-policy-incompatible`.

## 12. Fail-closed behavior

When `failClosed` is true, the gateway MUST NOT emit content for external use if extraction failed, the format cannot be inspected, the post-transform scan exceeds the accepted risk, a reversible vault cannot be encrypted, a required local detector or OCR engine is unavailable, or receipt integrity validation fails.

Diagnostic output MUST avoid echoing detected original values.

## 13. Conformance requirements

A conforming implementation MUST demonstrate that:

1. canonical direct identifiers do not occur in sanitized output;
2. receipts and logs contain no original detected values;
3. the same identifier is consistent inside one anonymized document;
4. anonymized identifiers are unlinkable across documents;
5. scoped pseudonyms are stable only within their declared scope;
6. reversible mappings are authenticated and encrypted;
7. unsupported binary formats fail closed;
8. post-transform scanning is independent of replacement generation;
9. all processing advertised as local performs no network call.

## 14. Security and limitations

Anonymization can fail through combinations of otherwise innocuous attributes, rare events, free-text narratives, model memorization, external datasets, document structure, or image content. Removing direct identifiers is not sufficient to guarantee that a person cannot be singled out or linked.

Implementations SHOULD provide domain-specific risk evaluation, human review for high-impact use cases, configurable generalization of quasi-identifiers, and periodic red-team datasets. Privacy receipts provide evidence of processing, not a certification of GDPR compliance or an absolute promise of anonymity.
